# Demo run report

Run on 2026-10-10 (Linux, Node 24.21.0, Python 3.13.16, Chromium 1194 headless) from branch `feature/demo-runs`. Every beat in `docs/PRESENTATION_SCRIPT.md`'s core path, plus the standalone fall-detection segment, was driven in a real browser against a production build. The 60-second synthetic check-in ran at the server's real one-reading-per-second cadence and was not accelerated. Only synthetic, fictional data was used. Tiger Data, Gemini, real Presage and hosting were not exercised (no credentials or camera here), so this report says nothing about them.

## Bigger issues (not changed)

1. **The approve dialog does not show the rest interval** (`apps/web/src/pages/Supervisor.tsx:531`). It only says "begins after the current protected break". The interval is computed client-side at confirm time and shown only on the card afterwards ("Approved rest: 6:24–6:29 PM"). Showing the computed start and end in the dialog would let the presenter point at "after the protected break" before confirming.
2. **The confirm buttons read "Confirm approve" / "Confirm acknowledge" / "Confirm resolve"** (`Supervisor.tsx:562`, `"Confirm " + selected.action`). The grammar is awkward, but e2e specs on other branches select these names, so a rename ("Confirm approval", and so on) needs coordinating.
3. **Two buttons start the same coverage preview**: "Plan coverage" in the header (`Supervisor.tsx:155`) and "Preview coverage proposal" in the coverage card. The script names only the second, so presenters may hesitate. Pick one label.
4. **The Integrations panel shows a technical fallback reason after any rehearsal on the same API process**: "Last explanation: deterministic (GEMINI_API_KEY or GEMINI_MODEL is not set)" (`apps/web/src/components/IntegrationsPanel.tsx:85`). The explainer state survives `/api/demo/reset`. It is honest but reads like an error on stage. Restart the API after rehearsing (DEMO.md pre-flight already says to stop it before `demo:reset`), or reset the explainer status on demo reset.
5. **An experimental tiredness estimate is visible**: "About 3.2 — likely between 3 and 4" (`apps/web/src/components/PersonalInsights.tsx:161`). The script never mentions it. A judge could read it as a fatigue measure, so presenters need a line for it (see below).
6. **The supervisor list polls every 2 s**, so the rest request and the assistance request take up to about 2–3 s to appear (B6 and B8 automation). Presenters should keep talking until the card appears instead of clicking ahead.
7. **Fall demo copy**: "1 anonymous track(s)" (`integrations/fall-detection/web/index.html:579`). Cosmetic.

## Rehearsal runner

`scripts/demo-rehearsal.ts` (`npm run demo:rehearse`) builds (unless `--no-build`) and starts `node apps/api/dist/server.js` on port 3622 with a freshly deleted `.data/rehearsal.sqlite`, `DEMO_MODE=true`, no Gemini or Presage. It also starts the fall-detection demo on 4362 with `.data/rehearsal-incidents.sqlite`. It drives worker and supervisor in separate Chromium contexts, so they get separate role cookies. It writes `timings.md`, `timings.json` and one PNG per beat (1366×860, about 100–150 KB each) to `.data/rehearsal/<timestamp>/` or `--out`. It exits non-zero if any beat fails and stops only the processes it started. `--base-url` drives an already running API instead (it calls the supervisor demo reset first). The screenshots in `docs/demo-screenshots/` come from that mode against the production server on port 3611.
